# JITAI の模擬（フェーズ 4）

過緊張を検知したワーカーに、近くの移動緑化ポッドでの短い休憩を勧める JITAI（Just-In-Time Adaptive Intervention）を、合成のワーカー集団で模擬します。4 段階を規則（アルゴリズム）で判断し、LLM は使いません（[integration-plan.md](integration-plan.md) の方針）。

```bash
uv run vmgs jitai --stage contracts/fixtures/stage.sample.json \
    --dispatch contracts/fixtures/dispatch.sample.json --scenario normal --out runs/jitai.json
```

- 入力: 地点データ `stage.json`、フェーズ 2 の配車 `dispatch.json`（契約 v1。`contracts/` は変えていない）、PET 用の気象（`--scenario`。既定は `dispatch.json` の `weather_scenario`）。
- `dispatch.json` が地点データと食い違う、気象・地点データに 8〜19 時がそろっていないときは、書き出さずに終了コード 1。
- `--workers`（既定 30）・`--seed`（既定 0）で合成の集団を決める。`--no-correction` は日内変動を補正しない検知（比較用）。
- 実データ・有料 API は使わない。サンプルの地点データで 1 秒程度。

## 4 段階

| 段階 | 判断 | 見送りの理由（`reason`） | コード |
| --- | --- | --- | --- |
| 1 検知 | 日内変動を差し引いた ln(HF) が、15 分続けて個人の揺らぎの −2 SD 以下 | （判定点にならない） | `vmgs.jitai.detect` |
| 2 予定 | 次の予定まで 20 分以上空いている | `in_meeting`（予定の最中）、`short_gap`（20 分未満） | `vmgs.jitai.calendar` |
| 3 ポッド | 徒歩 400 m 以内にポッドがあり、滞在の終わりまで同じ地点にいて、席が空いている | `no_pod_nearby`、`pod_leaving`、`pod_full` | `vmgs.jitai.pods` |
| 4 PET | ① 目的地（樹冠の下）の PET < 38℃、② 道中（日向）の PET < 42℃ | `pet_destination`、`pet_route` | `vmgs.jitai.safety` |

判定は 8:00〜18:55 の 5 分ごとに、全員を同じ時刻で進めます（席の予約は早い者勝ち）。過緊張の窓のうち、前の判定から十分に時間がたったものだけを判定点にします。

- 介入した後は 90 分判定しない（通知の負担を抑える。1 日の介入は多くて 7 回）
- 見送った後は 15 分後に判定し直す（過緊張が続いていて、予定が空けば拾い直す）

ポッドが複数あるときは近い順に見て、段階 3 を通ったもののうち段階 4 も通る最も近いものを選びます。どれも通らなければ、最も近いポッドで見送った理由を記録します。

### 段階 1: 日内変動を補正した過緊張の検知
HF（呼吸性の心拍変動、迷走神経の活動の指標）は夜に高く、日中の午後に低い日内変動を持ちます。固定の閾値では、午後の自然な低下を過緊張と取り違えます。

1. 個人の過去の勤務日（合成では 5 日）の ln(HF) に、24 時間周期の余弦 `mean + a·cos(ωt) + b·sin(ωt)` を最小二乗で当てはめる（cosinor）。
2. 当日の値から予測を引き、残差の頑健な SD（MAD × 1.4826。過去の日の過緊張に引っ張られないように）で割って z を求める。
3. 直近 3 窓（15 分）の z がすべて −2.0 以下なら過緊張。過去の値だけを使うので、その場で判定できる。計算できない窓（NaN。`vmgs.analysis.hrv.windowed_hrv` が覆いの不足で返す値）は根拠にしない。

閾値 −2.0・15 分の持続は、合成データで感度とエピソードの外の検知の釣り合いを見て決めた仮の値です（実データで決め直す）。

### 段階 2: 予定の空き枠
必要な空き = 滞在 10 分 + 徒歩圏の端までの往復 2 × 5 分 = 20 分。滞在 10 分は、フェーズ 5 の合成の R(t) の時定数 120 秒で 95% に達する約 6 分に余裕を足した長さです。

### 段階 3: 徒歩圏のポッドの空き
- 徒歩 80 m/分（不動産の表示に関する公正競争規約の徒歩所要時間の基準）。徒歩圏は片道 5 分 = 400 m。距離は直線（大円距離）で、道のりの迂回は見ていない。
- 位置は `dispatch.json` の時刻表（1 時間単位）。勤務地からの距離はその時の地点で測り、到着から滞在の終わりまで同じ地点にいるポッドだけを使う。時刻表に無い時は、そのポッドは使えない。
- 1 台の樹冠の下に同時に座れるのは 2 人（仮定。契約 v1 に席数は無い）。

### 段階 4: 二段階の PET 安全判定
PET はフェーズ 2 と同じ計算（`vmgs.fleet.comfort.PetTable`、[thermal.md](thermal.md)）です。往復にかかる時（出発の時から帰りの時まで）の最大値で判定します。

閾値は、高温多湿の地域向けの PET の温熱感の区分（Lin & Matzarakis 2008、台湾）に合わせました。中欧の区分（Matzarakis & Mayer 1996: 35〜41℃ 強い暑熱ストレス、41℃ 以上 極度）より約 4℃高く、東京の夏の暑熱順化に近いと考えました。

| PET [℃] | 温熱感 | 生理的な負荷 |
| --- | --- | --- |
| 34〜38 | warm | 中程度の暑熱ストレス |
| 38〜42 | hot | 強い暑熱ストレス |
| 42 以上 | very hot | 極度の暑熱ストレス |

1. **目的地（樹冠の下、ポッドあり）< 38℃**: 休憩の目的は回復です。強い暑熱ストレスに入ると回復を妨げる（フェーズ 5 の合成モデルでは PET 1℃あたり ln(HF) の到達値が 0.04 下がる）ので、その手前で止めます。
2. **道中（日向、ポッドなし）< 42℃**: 片道 5 分以内の短い歩行なので強い暑熱ストレスまでは許し、極度で止めます。道中は、勤務地に最も近い地点データの地点とポッドの地点の 2 か所で代表させます（経路上の日影は見ていない）。

限界: PET は座位に近い代謝（1.37 met）で計算しており、歩行中の負荷は過小です。区分は台湾の調査によるもので、東京での較正はしていません。

## 合成のワーカー（`vmgs.jitai.workers`）
ln(HF) は 5 分ごとの窓の値を直接作ります（1 日 × 多人数の拍を作ると重いため。実データでは RR から `windowed_hrv` で求める値に当たる）。

    lnHF(t) = b_s + c_s(t) + ou(t) + e(t) + Σ depth_k · 1[t ∈ エピソード k]
    c_s(t) = amp_s · cos(2π (t − acrophase_s) / 24 h)

| 項目 | 値 | 根拠・注意 |
| --- | --- | --- |
| 個人の水準 b_s | 平均 6.0、SD 0.5 | フェーズ 5 の `TrueParams` と同じ |
| 日内変動 | 振幅 0.5（SD 0.1）、頂点 4 時（SD 1 時間） | HF は夜間に高い。山と谷の差 1.0 ln 単位は仮定 |
| ゆっくりした揺らぎ | OU 過程、SD 0.2、時定数 30 分 | フェーズ 5 の `ou_process` を再利用 |
| 窓の推定誤差 | SD 0.1 | 仮定 |
| 過緊張のエピソード | 1 日 平均 1.5 回（Poisson）、9〜18 時に開始、20〜60 分、−0.8〜−1.2 | 急性ストレスで ln(HF) が 1 前後下がるという仮定。過去の日にも同じ割合で入れる |
| 予定 | 1 日 平均 4 件、30 分か 60 分、9:00〜18:00（昼休み 12〜13 時を除く） | 仮定 |
| 勤務地 | 地点データの地点のどれかから 300 m 以内 | 需要の集計と道中の PET には、勤務地に最も近い地点を使う |

## 出力（`runs/jitai.json`）
- `records`: 判定点ごとに、時刻・ワーカー（合成の ID）・結果（`intervened` / `skipped`）・見送った段階（`calendar` / `pods` / `pet`）と理由・ポッド・地点・道のり・PET（目的地と道中。環境の値）。
- `summary`: 判定の件数、介入の件数、介入率（介入 ÷ 判定）、段階別・理由別の見送り、検知の成績（合成の真のエピソードに対する感度と、エピソードの外の検知。補正あり・なしの両方。介入の影響を受けない、当日の元の系列での成績）、回復（`recovery`: 回復を反映した後に過緊張と判定した窓の数、エピソードの負担。全員の合計）。
- `demand`: 判定点を、勤務地に近い地点の**区画**（一辺 400 m、`zone_m`）・時刻ごとに数えた集計値。3 人未満の区画・時刻は区画としては出さない（`zones`）。落とした区画・時刻は時刻ごとに合算し、合算でも 3 人以上の時刻だけ件数を出す（`residual`、区画や人数は出さない）。区画の件数を区画内の地点に、合算の件数を全地点に等分して足したものが `cells` で、`stage.json` の `demand`（地点・時刻・重み）にそのまま写せる。書き戻しは `vmgs demand`（下記）。
- `rules`: 使った閾値。
- `message`（`--messages` のときだけ）: 介入した記録の通知文。見送った記録は `null`。全体の `messages` に、使った LLM と、テンプレートに戻した件数（`fallbacks`）。下記の「通知文」。

**個人の計測値は出さない。** ln(HF)・z・個人の基準は記録にも集計にも入れません（テストで出力の全文に無いことを確かめる）。合成のワーカーも、書き出すのは ID・判定・環境の値だけです。

## 通知文（`vmgs.jitai.message`）
介入の判断は上の 4 段階で済んでいるので、通知文は記録の事実を文章にするだけです。判断に LLM は使いません。

```bash
uv run vmgs jitai ... --messages                       # テンプレート（既定、LLM なし）
uv run vmgs jitai ... --messages --llm ollama:qwen3:8b # ローカルの ollama で言い換える（--llm だけでも可）
```

テンプレートの例（サンプルの地点データ、normal）:

> 11:05 次の予定まで 25 分あります。徒歩 1 分の丸の内 仲通りの広場にいる緑化ポッドで 10 分休みませんか。樹冠の下の体感温度は約 32℃ です。

| 事実 | 出どころ |
| --- | --- |
| 時刻 | 記録の判定時刻 |
| 空き時間 | 判定時刻から次の予定（無ければ終業 19:00）まで。`calendar.free_minutes` |
| 地点名 | `stage.json` の地点の `name` |
| 徒歩の分 | 記録の道のり ÷ 80 m/分の切り上げ（段階 3 と同じ） |
| 休憩の分 | 滞在 10 分（`pods.DWELL_MIN`） |
| 体感温度 | 記録の目的地（樹冠の下）の PET を整数に丸めた値 |

個人の計測値（HRV、z など）は事実に入れず、LLM にも渡しません。見送った記録には通知を出しません。

### LLM の言い換えと検査
`--llm ollama:<model>` のときだけ、上の事実とテンプレートの文をローカルの ollama に渡して言い換えさせます（`agent.llm.make_chat_model` を再利用、温度 0、思考オフ）。有料 API は受け付けません。小さなローカルモデルは数値を読み違えやすいので、出力を必ず事実と照合し、外れたらテンプレートに戻します。

| 検査 | 外れたときの理由（`llm_problems`） |
| --- | --- |
| 数値（全角は半角に直す）は、時刻の時・分、空き時間、徒歩の分、休憩の分、体感温度のどれか | `unknown_number:<値>` |
| `HH:MM` の形の時刻は、記録の時刻と同じ | `unknown_time:<時刻>` |
| 地点名が入っている／ほかの地点の名前が入っていない | `missing_spot`、`unknown_spot:<名前>` |
| 徒歩の分・休憩の分の数値が入っている | `missing_walk`、`missing_dwell` |
| 呼び出しが失敗した（接続・タイムアウトなど） | `llm_error:<例外の型>` |

`message` には、使った文（`text`）、`source`（`llm` / `template`）、LLM の出力（`llm_text`、`<think>` は除く）と外れた理由を残します。テストは偽の応答で検査の振る舞いだけを確かめ、実際の ollama は呼びません。

限界: 検査は事実（数値・時刻・地点名）の照合だけで、文の意味は見ていません。qwen3:8b で試した 11 件はすべて検査を通りましたが、誘いの文でなくなったもの（「〜の緑化ポッドにいます。」「〜の緑化ポッドで、樹冠の下の体感温度は約 32℃ です。」）が 3 件ありました。漢数字（「十分」）は「十分に」と区別できないので数値として読みません。時刻の分（例: 05）と同じ数値は、ほかの場所に出ても数値の検査では見逃します（徒歩の分の取り違えは `missing_walk` で拾う）。

| seed | 感度（補正あり） | 感度（補正なし） | エピソードの無い集団の誤検知の窓: 補正あり（うち 13 時以降） | 補正なし（うち 13 時以降） |
| --- | --- | --- | --- | --- |

- 補正なしの誤検知は**すべて 13 時以降**（日内変動の谷）に出ました。補正ありは時刻に偏りません。
- 補正すると感度が 7〜21 ポイント上がりました。

## 介入後の回復（R(t)）の反映

介入すると、その後の ln(HF) に回復分を足し、次の判定に反映します（既定で有効。`--no-recovery` で無効、`--carryover-min` で持ち越しの長さを変える）。判定は各時刻に「直近 3 窓の z」から行うので、回復して z が −2 を上回れば、それ以降は過緊張と判定しません（`vmgs.jitai.recovery`、`vmgs.jitai.engine.run_jitai`）。

### 回復のモデル（前提）
- **滞在中**（到着から 10 分）: フェーズ 5 の合成モデルと同じ 1 次の立ち上がり A·(1 − e^{−s/τ})。τ = 120 秒と係数は `vmgs.analysis.synthetic.TrueParams` を共有し、振幅の式も `response_amplitude` として共有しています（フェーズ 5 の合成データは変わらないことをテストで確かめた）。
  - A = 0.2 × 離脱（1）+ 0.6 × 緑の量 − 0.04 × (目的地の PET − 26) − 0.02 × (騒音 − 55)
  - 緑の量はポッドの樹冠の下として **0.8（仮定）**、騒音は基準値の 55 dB（地点データに騒音が無いため、効果 0）。
  - 例: 目的地の PET 30℃ で A ≈ 0.52、37℃ で A ≈ 0.24。エピソードの下げ幅（0.8〜1.2）の一部しか戻りません。
- **帰った後**: 滞在の終わりの値が、時定数 30 分で指数的に減ります（持ち越し）。**この 30 分には根拠がありません。** フェーズ 5 は接触中の 10 分しか扱っていないため、0・30・60 分で比べています。
- エピソードの負担 = 真のエピソードの窓ごとの「下げ幅 − 回復分」の正の部分 × 5 分（ln × 分）。検知に頼らない、真の値での評価です。

### 結果（地点データの 255 地点、集計した需要での配車、ワーカー 300 人・seed 1）

| 気象 | 回復 | 判定 | 介入 | 過緊張の窓 | エピソードの負担 |
| --- | --- | --- | --- | --- | --- |
| normal | なし | 771 | 106 | 2357 | 18140 |
| normal | 持ち越し 0 分 | 771 | 106 | 2222（−5.7%） | 17792（−1.9%） |
| normal | 持ち越し 30 分 | 769 | 106 | 2112（−10.4%） | 17083（−5.8%） |
| normal | 持ち越し 60 分 | 763 | 105 | 2065（−12.4%） | 16836（−7.2%） |
| heatwave | なし | 917 | 15 | 2357 | 18140 |
| heatwave | 持ち越し 30 分 | 917 | 15 | 2338（−0.8%） | 18037（−0.6%） |

- normal・持ち越し 30 分で、介入 1 回あたり過緊張の窓が約 2.3 窓（約 12 分）減りました。集団全体では 10% の減少です。介入できたのは、真のエピソード 437 件に対して 106 回だけなので、全体の減り方は小さくなります。
- 猛暑では、介入そのものが 15 回しかありません（道中の PET で見送る）。目的地の PET も高いので、1 回あたりの回復も小さく、ほとんど減りません。
- 持ち越しを長くするほど減りますが、その長さには根拠がありません。実験で、休憩の後の ln(HF) を追って決める必要があります。
- 回復すると、後の判定（過緊張の検知）が減ります。判定の件数も少し減ります（771 → 763）。需要の集計（判定点の数）にも反映されます。

## 需要の書き戻し（`vmgs demand`）

JITAI の需要の集計を、地点データ `stage.json` の `demand` に書き戻します。書き戻した地点データで `vmgs dispatch` を回すと、既定の需要（8〜19 時に全地点 1.0）の代わりに、集計した需要で配車します。

```bash
uv run vmgs dispatch --stage stage.json --scenario normal --out runs/d0.json   # 既定の需要
uv run vmgs jitai --stage stage.json --dispatch runs/d0.json --scenario normal --workers 300 --out runs/j0.json
uv run vmgs demand --stage stage.json --jitai runs/j0.json --out runs/stage.demand.json
uv run vmgs dispatch --stage runs/stage.demand.json --scenario normal --out runs/d1.json  # 集計した需要
```

- 元の `stage.json` は上書きしない（`--out` が同じファイルなら終了コード 1）。全地点の `demand` を置き換える（足し合わせない）。
- 区域・日付が地点データと違う、地点データにない地点を含む、集計が空のときは、書き出さずに終了コード 1。集計が空のまま書き戻すと、配車が黙って既定の需要に戻るため。
- `weight` は判定点の件数を区画内の地点数で割った値（相対値。正規化しない）。
- **判定点は、介入しない場合のもの**（`vmgs.jitai.engine.latent_decisions`。`jitai.json` の `demand.basis` は `no_intervention`）。介入が無ければ判定は毎回見送りで、次の判定は 15 分後、回復も入らないので、判定点はワーカーの ln(HF) の系列だけで決まり、配車・PET・予定に左右されません。介入した後の記録で数えると、配車と需要の反復が往復しました（下の「反復の性質」）。地図アプリに渡す区画の集計（`jitai-summary.json`）は、今までどおり介入した後の記録で数えます。
- この節と「介入後の回復」の節の結果の表は、介入した後の記録で需要を数えていたときの値です。

### 集計の単位を地点から区画に広げた理由
最初は地点 × 時刻で数えていましたが、地点データの 255 地点では、ワーカー 30 人で 0 セル、300 人でも 4 地点、1000 人でも 42 地点にしか需要が残りませんでした。1 つのセルにいる人がほぼ 1〜2 人で、3 人未満を消す規則（個人の特定を防ぐ）に引っかかるためです。実際の研究も参加者は少ないので、同じことが起きます。

そこで、区域を南西の角から 400 m 四方（徒歩圏の片道に合わせた）の区画に切り、区画 × 時刻で人数を数えてから 3 人未満を消し、残った件数を区画内の地点に等分するようにしました（`vmgs.jitai.demand.demand_zones`、`vmgs.jitai.engine.demand_zone_counts`）。区画の中では、どの地点にポッドを置いても徒歩圏に入るという考えです。3 人未満で落とした分は、のちに時刻ごとに合算して全地点に等分するようにしました（下の「直した後も残った悪化の理由」）。

### 結果（地点データの 255 地点、2025-08-30、ポッド 3 台）

需要が残った範囲（seed 0）:

| ワーカー | 区画 × 時刻 | 区画 | 需要のある地点 | 時刻 |
| --- | --- | --- | --- | --- |
| 30 | 1 | 1 | 21 | 11 時 |
| 100 | 11〜13 | 6 | 117 | 9〜17 時（16 時を除く） |
| 300 | 86〜94 | 16 | 238 | 9〜18 時 |

30 人では区画にしても 1 区画・1 時刻しか残りません。需要の形を見るには 100 人以上が要ります。

一様の需要と、集計した需要での配車の比較（JITAI の介入率。集計はワーカー 300 人・seed 0 から作った）:

| 気象 | 評価の集団 | 一様の需要 | 集計した需要 |
| --- | --- | --- | --- |
| normal | seed 0（集計と同じ集団） | 9.3% | 17.2% |
| normal | seed 1 | 7.7% | 13.7% |
| normal | seed 2 | 8.5% | 16.1% |
| heatwave | seed 0（集計と同じ集団） | 0.5% | 2.9% |
| heatwave | seed 1 | 0.3% | 1.6% |
| heatwave | seed 2 | 0.9% | 1.8% |

- 集計した需要で配車すると、介入率がおよそ 2 倍になりました。集計に使っていない集団（seed 1・2）でも上がるので、同じ集団に合わせ込んだだけではありません。
- ただし、合成のワーカーの勤務地と過緊張の起き方は seed が違っても同じ分布から作っているので、「需要の分布が変わらない」前提の上での結果です。
- 猛暑では、道中の PET による見送りが多いため、介入率そのものは低いままです。

## 全体を 1 コマンドで回す（`vmgs loop`）

配車 → JITAI → 需要の書き戻し を、`--rounds` の回数だけ繰り返します。各段階は `vmgs dispatch`・`vmgs jitai`・`vmgs demand` と同じ関数を呼びます。

```bash
uv run vmgs loop --stage stage.json --scenario normal --workers 300 --rounds 1 --out-dir runs/loop
```

- 周 0 は入力の地点データのまま配車します（需要が空なら一様の需要）。周 r の JITAI の集計を書き戻したものが、周 r+1 の地点データです。
- `--out-dir` に、周ごとの `stage.rN.json`・`dispatch.rN.json`・`jitai.rN.json`・`jitai-summary.rN.json` と、表（`summary.md`・`summary.json`）を書きます。
- `jitai-summary.rN.json` は、地図アプリに渡す集計です（契約 v1 の `jitai-summary.schema.json`。`vmgs jitai --summary-out` でも書き出せる）。区画（400 m）× 時刻ごとの判定・介入・段階別の見送りの件数だけで、3 人未満の区画・時刻は入れません。個人の記録・ID も入れません。

### 結果（地点データの 255 地点・建物だけの遮蔽、ワーカー 300 人・seed 0、回復あり・持ち越し 30 分）

| 気象 | 周 | 需要 | 需要の地点 | 判定 | 介入 | 介入率 | 過緊張の窓 | エピソードの負担 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| normal | 0 | 一様 | — | 834 | 77 | 9.2% | 2220 | 17876 |
| normal | 1 | 集計 | 238 | 762 | 131 | 17.2% | 2097 | 17391 |
| heatwave | 0 | 一様 | — | 939 | 5 | 0.5% | 2385 | 18555 |
| heatwave | 1 | 集計 | 238 | 912 | 26 | 2.9% | 2351 | 18381 |

回復を反映しても、集計した需要で配車し直すと介入率がおよそ 2 倍（normal 9.2% → 17.2%）になる点は、回復を入れる前の結果と同じです。過緊張の窓は 5.5%（normal）減りました。

### 反復の性質（`--rounds 5`、ワーカー 300 人、回復あり・持ち越し 30 分）

地点データは、街路樹の樹冠を加えた遮蔽（地図アプリの PR stzn/tokyo-green-simulator#11 の `otemachi.json`）。normal・heatwave × seed 0〜2 と、比較に建物だけの遮蔽（v1）の seed 0 を回しました。表の値は介入率（介入 ÷ 判定）。L1 は前の周との需要の分布（合計 1）の差です。

| 遮蔽 | 気象 | seed | 周 0 | 周 1 | 周 2 | 周 3 | 周 4 | 周 5 | 周 3〜5 の L1 | 終わり方 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 建物＋樹冠 | normal | 0 | 11.7% | 16.3% | 8.5% | 9.5% | 10.7% | 9.5% | 0.32〜0.34 | 揺れ続ける |
| 建物＋樹冠 | normal | 1 | 10.8% | 15.4% | 8.9% | 12.3% | 8.4% | 12.3% | 0.32〜0.37 | 揺れ続ける |
| 建物＋樹冠 | normal | 2 | 12.9% | 6.8% | 11.7% | 6.8% | 11.7% | 6.8% | 0.099 | 周期 2 で往復 |
| 建物＋樹冠 | heatwave | 0 | 1.5% | 4.6% | 3.9% | 5.1% | 3.9% | 5.1% | 0.036 | 周期 2 で往復 |
| 建物＋樹冠 | heatwave | 1 | 1.3% | 10.1% | 9.1% | 7.3% | 9.5% | 7.1% | 0.04〜0.08 | 揺れ続ける（小さい） |
| 建物＋樹冠 | heatwave | 2 | 1.4% | 2.2% | 1.4% | 1.4% | 1.4% | 1.4% | 0.000 | 周 3 で固定点 |
| 建物だけ | normal | 0 | 9.2% | 17.2% | 10.4% | 11.7% | 8.4% | 11.7% | 0.32 | 揺れ続ける |
| 建物だけ | heatwave | 0 | 0.5% | 2.9% | 2.2% | 2.9% | 2.2% | 2.9% | 0.013 | 周期 2 で往復 |

読み取り:
- **収束しない**。8 通りのうち固定点に落ち着いたのは 1 通りだけです。3 通りは周期 2 で同じ 2 つの地点データを往復し（周 r と周 r+2 の `stage.json` がファイルとして一致）、残りは周 2 以降も前の周との L1 が 0.3 前後のまま揺れ続けます。
- **周 1 がいちばん良い**。normal では、一様の需要（周 0）から集計の需要（周 1）に替えると介入率が上がります（9〜17%）が、周 2 で下がり、その後は周 0 と同じくらいか、それより低いところを往復します。過緊張の窓・エピソードの負担も同じ動きです。
- **街路樹の樹冠**：周 0 の介入率は、normal 9.2% → 11.7%、heatwave 0.5% → 1.5%（seed 0）と上がりました。日影が増えて地点の PET が下がり、PET の段階での見送りが減ったためです。反復が揺れる性質は、建物だけの遮蔽と変わりません。

原因（考え）: 需要は「過緊張の判定点の件数」を区画ごとに数えたものです。ポッドを置いた区画では、介入と回復（持ち越し 30 分）で次の判定が減り、ポッドの来ない区画では減りません。そのため、周 r でポッドを置いた区画ほど周 r+1 の需要が小さく出て、ポッドが別の区画へ移り、周 r+2 で元に戻ります。**測っている需要が、その周の配車の結果に左右される**（配車への応答を含む）ことが、往復の原因だと考えます。v1 と樹冠で同じ性質が出るので、遮蔽の計算とは関係ありません。

直し方の候補（1 を採用。下の「需要を介入しない場合の判定点で数えた後」）:
1. **介入しない場合の需要を数える**：JITAI を介入なしでも回し（判定だけ）、その判定点で需要を作る。配車に左右されないので 1 周で決まり、反復は要らなくなる
2. **周をまたいで平滑化する**：需要 = (1 − α)・前の周の需要 + α・今の周の集計（α = 0.5 など）。往復は小さくなるが、配車への応答を含む点は残る
3. **今のまま、周 1 を使う**：反復は 1 回だけと決め、`--rounds 1` を既定の使い方にする

- heatwave では、集計の需要で配車すると介入率が上がり（1.3〜1.5% → 2.2〜9.9%）、過緊張の窓・負担も減ります。
- **normal の seed 0 と seed 2 では、集計の需要の方が一様の需要より悪くなりました**（介入率 11.7% → 9.5%、12.9% → 6.8%。窓・負担も増える）。介入しない場合の判定点が多い区画・時刻へポッドを寄せても、その時刻にワーカーの予定が空いていなかったり、PET で見送られたりすれば介入にならないためと考えます（配車は需要だけを見て、予定・PET による見送りは見ない）。そこで次の節のとおり、予定の空いた判定点だけを数えるようにしました。

## 条件 × seed で比べる（`vmgs sweep`）

合成のワーカーの組（seed）による違いが、条件の違いより大きいことがあります（上の 3 seed の表）。そこで、条件（気象 × ポッドの台数）× seed で `vmgs loop` を回し、**同じ seed どうしの差（対）**の平均と 95% 信頼区間（t 分布）で比べます。

```bash
uv run vmgs sweep --stage stage.json --scenarios normal heatwave --pods 3 5 \
    --seeds 10 --workers 300 --rounds 1 --out-dir runs/sweep --jobs 4
```

- `--out-dir` に、実行ごとの `<気象>-p<台数>/seed<k>/`（`vmgs loop` の出力）、1 行 = 条件 × seed × 周の `runs.csv`、まとめの `summary.md`・`summary.json` を書きます。
- まとめは 3 つ: 条件 × 周の平均と CI、**周の差**（周 r − 周 0。一様の需要 → 集計の需要）、**台数の差**（同じ気象・seed・周で、最初の台数との差）。「良くなった」は良い向き（介入率は大きい方、過緊張の窓・負担は小さい方）に動いた seed の数です。
- 引数（地点データ・気象・台数・seed・ワーカー数・周回数）が同じ実行の結果があれば回し直しません。途中で止めても、同じコマンドで続きから回せます。`--jobs` で並列に回せます（seed で乱数が決まるので結果は同じ）。
- 信頼区間はワーカーの組の違いだけを表します。地点データ・気象・前提の値（閾値・持ち越し・緑の量）の不確かさは含みません。

### 結果: 集計の需要は一様の需要より良いか（樹冠ありの地点データ 255 地点、ポッド 3 台、ワーカー 300 人、seed 0〜9）

需要は予定の空いた判定点（`no_intervention_free_time`）。並列 4 で約 2 分半。

| 指標 | 気象 | 周 0（一様）の平均 | 周 1 − 周 0（95% CI） | 良くなった seed |
| --- | --- | --- | --- | --- |
| 介入率 | normal | 11.8% | +0.5pt（−1.8〜+2.8pt） | 4/10 |
| 介入率 | heatwave | 1.7% | **+2.3pt（+0.6〜+4.1pt）** | 10/10 |
| 過緊張の窓 | normal | 2254 | −18（−57〜+21） | 5/10 |
| 過緊張の窓 | heatwave | 2443 | **−33（−52〜−14）** | 9/10 |
| エピソードの負担 | normal | 18272 | −40（−184〜+104） | 5/10 |
| エピソードの負担 | heatwave | 19087 | **−127（−204〜−51）** | 10/10 |

読み取り:
- **heatwave では、集計の需要の方が良い**ことが、3 指標とも CI が 0 をまたがずに言えます（介入率 1.7% → 4.0%）。一様の需要では、PET の高い時刻・地点にもポッドを均等に置き、そこで見送りが続くためと考えます。
- **normal では差が見えません**（CI が 0 をまたぎ、良くなった seed は 4〜5/10）。3 seed の表で seed 0・2 が一様より悪かったのは、この揺れの範囲です。
- 次の「配車の見直し」（台数・置き方）は、この `vmgs sweep` の台数の差で比べます。

### 結果: 配車の方式と台数（樹冠ありの地点データ 255 地点、ワーカー 300 人、seed 0〜9）

`vmgs sweep --scenarios normal heatwave --policies greedy coverage --pods 3 5 8 --seeds 10 --rounds 1`（120 実行、並列 4 で約 20 分）。coverage は徒歩圏で覆える需要を見る配車（[dispatch.md](dispatch.md)）。周 0 は一様の需要、周 1 は集計の需要（予定の空いた判定点）。

介入率の平均（95% CI）:

| 気象 | 方式 | 3 台・周 0 | 3 台・周 1 | 5 台・周 0 | 5 台・周 1 | 8 台・周 0 | 8 台・周 1 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| normal | greedy | 11.8% | 12.3% | 14.0% | 16.0% | 20.9% | 22.9% |
| normal | coverage | **20.9%** | **22.1%** | **35.7%** | 35.5% | **48.0%** | 47.9% |
| heatwave | greedy | 1.7% | 4.0% | 2.0% | 4.9% | 3.2% | 7.2% |
| heatwave | coverage | **7.8%** | 7.7% | **14.3%** | 10.3% | **14.8%** | 13.0% |

greedy・3 台との差（同じ seed で対、周 0）: coverage・3 台は normal +9.1pt（+7.8〜+10.4）、heatwave +6.2pt（+5.6〜+6.8）で、10/10 の seed で良くなりました。過緊張の窓（normal −119、heatwave −62）・エピソードの負担（normal −464、heatwave −278）も、CI が 0 をまたがずに減ります。

周の差（周 1 − 周 0、集計の需要は一様より良いか）:

| 気象 | 方式 | 3 台 | 5 台 | 8 台 |
| --- | --- | --- | --- | --- |
| normal | greedy | +0.5pt（−1.8〜+2.8） | +2.0pt（−1.4〜+5.5） | +2.0pt（−2.0〜+6.0） |
| normal | coverage | +1.1pt（+0.2〜+2.0） | −0.2pt（−1.2〜+0.8） | −0.1pt（−0.9〜+0.7） |
| heatwave | greedy | **+2.3pt（+0.6〜+4.1）** | **+2.9pt（+1.2〜+4.6）** | **+4.0pt（+2.2〜+5.8）** |
| heatwave | coverage | −0.2pt（−1.8〜+1.5） | **−4.0pt（−5.6〜−2.4）** | **−1.8pt（−2.9〜−0.7）** |

読み取り:
- **置き方の効果が大きい**。coverage・3 台は greedy・8 台と同じ介入率（normal 20.9%）で、台数を増やすより置き方を変える方が効きます。greedy は需要のある地点そのものにしか価値を付けず、近くに重ねて置いて同じワーカーを二重に数え、JITAI が見送る PET の高い地点にも置いていました。
- **coverage では、集計の需要に替えても良くならない**。normal は差がほぼ無く、heatwave の 5・8 台では悪くなりました。greedy で集計の需要が効いていたのは、地点ごとの価値の偏りを需要が補っていたためで、coverage が徒歩圏と PET を直接見るようになると、その分の効き目が無くなったと考えます。heatwave で悪くなる理由は、下の 2 つの節（道中の PET、3 人未満の区画を落とすこと）。
- 既定の方式は、この結果と下の 2 つの修正の後に coverage へ切り替えました（`vmgs dispatch`・`vmgs loop`・`vmgs sweep`）。

### coverage が heatwave で集計の需要に替えると悪くなった理由と、直した後

heatwave・coverage・5 台で、周 1 は周 0 より介入が平均 29 件減り、道中の PET による見送り（`pet_route`）が 79 件増えていました。JITAI の道中の PET は、勤務地とポッドの地点の**日向の** PET の最大で、42℃ 以上なら見送ります（`vmgs.jitai.safety.pet_check`）。増えた `pet_route` を分けると（10 seed 合計）、ポッドの地点だけが暑いものが 929 → 1653 件、勤務地とポッドの両方が暑いものが 819 → 1176 件と増え、勤務地だけが暑いものは 512 → 226 件に減っていました。集計の需要は 12〜17 時に寄っており、coverage は PET の下がり幅が大きい日向の地点を選ぶので、暑い時刻に日向へポッドを置き、JITAI がそれを道中の暑さで使わない、ということが起きていました。coverage の安全の条件が「目的地の樹冠下 38℃ 未満」だけで、JITAI の「道中 42℃ 未満」を見ていなかったのが原因です。

そこで coverage の条件に「ポッドの地点の日向 PET が 42℃ 未満」（`FleetParams.max_route_pet_c`、`ROUTE_PET_MAX_C` と同じ値）を足しました。同じ条件（seed 0〜9）で回し直した結果:

| 気象 | 台数 | 介入率 周 0（前 → 後） | 介入率 周 1（前 → 後） | 周 1 − 周 0（前 → 後） |
| --- | --- | --- | --- | --- |
| heatwave | 3 | 7.8% → **15.4%** | 7.7% → **15.4%** | −0.2pt → +0.1pt（−0.7〜+0.8） |
| heatwave | 5 | 14.3% → **23.6%** | 10.3% → **21.9%** | −4.0pt → −1.7pt（−2.5〜−0.8） |
| heatwave | 8 | 14.8% → **28.2%** | 13.0% → **27.3%** | −1.8pt → −0.9pt（−1.7〜−0.1） |
| normal | 3・5・8 | 変わらず（日向でも 42℃ に届かない） | 変わらず | 変わらず |

- heatwave の介入率はおよそ 2 倍になり、悪くなった条件はありません。
- 集計の需要に替えたときの悪化は小さくなりましたが、5・8 台ではまだ CI が 0 をまたがずに残ります（−1.7pt、−0.9pt）。理由は次の節。

### 直した後も残った悪化の理由（3 人未満の区画を落とすこと）と、合算して配った後

heatwave・coverage・5 台で、周 1 の判定点（予定で見送ったものを除く）を、勤務地の区画・時刻が需要の集計に残ったかで分けました（10 seed 合計）:

| 勤務地の区画・時刻 | 判定 | 介入率 | 徒歩圏にポッドなし |
| --- | --- | --- | --- |
| 3 人以上で需要に残った | 3452 | 37.2%（周 0 は 35.2%） | 18.8% |
| 1〜2 人で需要から落ちた | 1742 | **19.9%**（周 0 は 31.1%） | **56.2%** |

判定の約 3 分の 1 が、3 人未満を消す規則（個人の特定を防ぐ）で需要 0 になった区画・時刻から出ていました。coverage はそこにポッドを置く価値を 0 とみなすので、徒歩圏にポッドが無くなります。需要に残った所では良くなっており、悪化はすべて落とした所から来ていました。区画・時刻ごとの人数は 1 人が 498、2 人が 388 と、半分以上が 3 人未満です（ワーカー 300 人、20 区画）。

そこで、落とした区画・時刻を**時刻ごとに合算**し、合算で 3 人以上なら全地点に等分して足すようにしました（`vmgs.jitai.engine.demand_residual_counts`、出力は `demand.residual` に時刻・件数・配る地点の数だけ。区画や人数は出さない）。同じ条件で回し直した結果（周 1 − 周 0）:

| 気象 | 3 台（前 → 後） | 5 台（前 → 後） | 8 台（前 → 後） |
| --- | --- | --- | --- |
| normal | +1.1pt → +1.1pt（+0.3〜+1.8） | −0.2pt → +0.3pt（−0.4〜+0.9） | −0.1pt → **+1.5pt（+0.1〜+2.9）** |
| heatwave | +0.1pt → −0.1pt（−0.6〜+0.5） | −1.7pt → **−1.4pt（−2.1〜−0.7）** | −0.9pt → −0.4pt（−1.0〜+0.1） |

- 悪くなった条件は無く、heatwave・8 台の悪化は CI が 0 をまたぐようになり、normal・8 台は集計の需要の方が良くなりました。周 0（一様の需要）の結果は変わりません。
- heatwave・5 台には −1.4pt が残ります。落とした所の介入率は 19.9% → 22.2% と少し戻っただけです。合算した分は全 255 地点に薄く配られ、区画の需要（区画内の十数地点に配る）に比べて 1 地点あたりの重みが小さいためです。少人数の所を覆うには、匿名性の規則（3 人）か区画の大きさ（400 m）を変える必要があり、どちらも参加者の人数が決まってから決めます（未決事項）。

## 未決事項
- 閾値（z −2.0・15 分、PET 38/42℃、徒歩 400 m、席 2）は仮の値。実データ（倫理審査の後）で決め直す。
- 需要の区画の大きさ（400 m）と、3 人未満を消す閾値は仮の値。参加者の人数が決まったら見直す。
- 回復の持ち越しの長さ（30 分）とポッドの緑の量（0.8）は仮の値。休憩の後も ln(HF) を追う実験で決める。
