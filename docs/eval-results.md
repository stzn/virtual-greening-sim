### 各版の変更と学び
- **v3**: 判断を「上から順に評価する条件→行動」のチェックリストにし、暑熱緩和を副次目的へ格下げ、座標を固定。
  → 雨でも散水する問題が解消。一方、条件を誤判定し、行動を最終回答に書くだけでツールを呼ばない失敗が残った。
- **v4**: 各行を数値で ○/× 判定した判断メモを書かせ、「ツールを呼んでいない行動は実行したと書かない」を明記。
  → 乾燥・猛暑退避は解消したが、雨で `get_weather` を呼ばず散水、タンク120mlで1000mlを試みる退行。
- **v5**: 「両方の観測結果を得るまで行動ツールを呼ばない」「散水量は1000mlと残量の小さい方」を明文化。→ 7/8。
- **残課題**: 「直前にA→Bへ退避した直後、Bで適正水分なのに Aへ戻る」（往復）。チェックリスト #5（何もしない）に反して移動している。

### 評価設計・手法についての学び
1. **試行がほぼ同一**: temperature=0 のため、5回の試行は全シナリオでトレースが完全一致（異なるトレース数=1）。
   実質の標本数は1で、「5回中4回」は統計的な意味を持たない。→ 試行ごとに初期値を少し振る（水分±数%、タンク量、気温）か、temperature>0 にする。
2. **プロンプト修正は他の挙動を動かす**: v3→v4 は2件直して別の2件を壊した。1件ずつの修正でなく、毎回全シナリオで回帰を見る必要がある（評価シナリオの価値）。
3. **シナリオが学習データ化する危険**: 評価シナリオに合わせてルールを書いているため、合格率は汎化性能を意味しない。未見の状況（フェーズ3の24時間シミュレーション）で確認する。
4. **「行動しない」系だけの評価は空振りを許す**: 「行動すべき」系を対で用意したから v1 を検出できた。
5. **思考オフのモデルは条件判定が雑**: 数値を書かせる、観測の前提条件を明文化する、が効いた。思考オン（1呼び出し数十秒）との比較は未実施。

## 2026-10-20 往復移動の対策（v6 + 世界側ガード）

### 構造的な対策（BDD: tests/features/world/movement.feature ほか）
1. **世界側ガード**: 直前の移動元へ2時間以内に戻る `move_to_spot` を `RECENT_REVERSAL` で拒否（エラーに `retry_after_hours`）。
   健康度 50 未満は緊急として許可。LLM が誤っても往復が起きない安全網（決定論テストで保証）。
2. **観測の追加**: `get_plant_state` が `last_move`（from / to / hours_ago）を返す。履歴の文章に頼らず構造化データで読める。
3. **プロンプト v6**: `last_move` の読み方と往復禁止を明記（v5 からの差分はこの1項目のみ）。

### 結果（v6、全9シナリオ）: 8/9 合格・回帰なし
| シナリオ | v5 | v6 |
| --- | --- | --- |
| 雨予報 / 乾燥 / 猛暑退避 / 日影 / バッテリー少 / 状態確認 / タンク上限（7件） | 5/5 | 5/5 |
| 直前に移動 → 戻らない【履歴の文章のみ・世界に記録なし】 | 0/5 | **0/5** |
| 直前の移動が世界にも記録されている → 往復を**試みない**（新規） | － | **5/5** |

### 解釈
- 世界にも `last_move` がある**現実的な状況**では、LLM は `last_move` を読んで往復を試みない（5/5）。さらにガードがあるため、仮に試みても移動は成立しない（二重の安全策）。
- **履歴の文章だけ**を与える元のシナリオは 0/5 のまま。この状態（世界に記録が無いのに履歴だけ「移動した」）は実際のシミュレーションでは起きない。
  ただし「LLM は文章の履歴を判断に使えていない」という弱さは残っている（ターン間の持ち越しを文章で行う設計の限界）。
  シナリオは失敗を隠さず残している。フェーズ3で24時間通しの挙動を見て、必要なら履歴の渡し方（構造化）を見直す。
- 学び: LLM の誤りを**プロンプトで直す**より、**世界のルールで不可能にし、必要な事実を構造化データで観測させる**ほうが堅牢（失敗が決定論的テストで保証できる）。

5. tradeoff では hybrid も free も、日影へ退避せず歩道Cで散水し続けて暑熱緩和は大きい（42.6 / 53.0、baseline 11.9）が、植物の健康度は下がる。**散水で都市を冷やすことを優先し、植物の安全を後回しにしている**。

## 2026-10-22 計画観測（残り時間あたりの水・電池）: 観測は届いたが、使われなかった

hybrid の文章のヒントでは水の配分が改善しなかった（往復移動のときは、文章ではなく世界側の観測で解決した）。
そこで `get_plant_state` に**計算値だけ**を返す計画観測を足した（BDD: tests/features/world|sim/planning_observation*.feature ほか。変異テスト7件を全て検出）。

| キー | 定義 |
| --- | --- |
| `hours_remaining` | 終了時刻までの残りターン数（現在を含む。24時間なら開始時 24） |
| `water_per_remaining_hour_ml` | 水タンク残量 ÷ 残り時間 |
| `battery_per_remaining_hour_pct` | バッテリー残量 ÷ 残り時間 |

- 既定はオフ（オフのときの出力は従来と同一）。終了時刻は設定（開始時刻 + 時間数）由来で、再開しても同じ。
- プロンプト `plan` = `hybrid` + 観測の説明1文（数字・閾値なし。差分はその1文だけ）。`plan` を選んだ構成にだけ観測が有効（他の構成の世界は変わらない）。
- 比較の解釈: hybrid と plan の差は「観測 + 説明1文」のセットで、観測だけの効果は切り分けていない。

### 結果（scarce_water、qwen3:14b、temperature=0、3バリアント。baseline〜hybrid は前回の実行を再利用）
| 構成 | 最終健康度 | ベースライン比（勝/分/負） | 成功した行動 | 失敗（INSUFFICIENT_WATER など） |
| --- | --- | --- | --- | --- |
| baseline | 69.8±14.5 | － | | |
| v9 | 73.6±18.4 | 2 / 0 / 1 | 9 | 1 |
| free | 61.0±19.7 | 1 / 0 / 2 | 12 | 13 |
| hybrid | 55.3±18.1 | 0 / 0 / 3 | 22 | 6 |
| **plan（観測あり）** | **55.7±16.4** | 0 / 0 / 3 | 26 | **21**（INSUFFICIENT_WATER 17、VALIDATION_ERROR 3） |

### 読み方（ログの全文で確認した事実のみ）
1. **改善しなかった**: plan 55.7 は hybrid 55.3 と同等（3バリアントとも負け）。差はばらつき（標準偏差16〜18）の範囲内。
2. **観測はモデルに届いていた**: 例として、00時に `water_tank_ml=1146, hours_remaining=24, water_per_remaining_hour_ml=47.8`。値は正しい。
3. **しかしモデルは観測をほぼ使っていない**: plan の判断理由（72ステップ）のうち、観測や配分に触れたのは**1ステップだけ**（hybrid は0）。
   「観測の値に引きずられて小分けにした」という推測は、判断理由に根拠が無いため**採らない**（100ml 刻みは 47.8ml/時とも比例しない）。
4. **ツールの失敗が増えた**: plan の失敗21回の内訳は INSUFFICIENT_WATER 17・VALIDATION_ERROR 3・ALREADY_AT_SPOT 1。水が残り少ないのに、残量を超える（または下限 50ml 未満の）散水を繰り返し要求している。
   v7 の移動予算の文章ヒントが無視されたときと同じ構図。
5. 水がもともと足りない状況（全員が最後は tank=0）で、改善の上限は限られる。

### 学び
- **観測を足すだけでは、使われなければ効かない**。往復移動のときに効いたのは、観測だけでなく、**判断の枠組み（v8 のチェックリストの条件欄）に組み込んだ**から（v7 の文章だけでは 0/5、v8 で 5/5）。
- 自由形式のプロンプトでは、観測を判断に組み込ませる手段が無い。「判断基準を与えない（free）」と「観測を使わせる」は両立しにくい。

### 限界
- n=3・単一モデル・temperature=0。「改善の証拠が無い」であって「効果が無い」とは言えない。
- 観測だけ（説明1文なし）の腕は未実施。

### 次の候補
1. **観測を判断の枠組みに組み込む**（チェックリストの条件欄に、観測を使う1行を足す）。ただしルールを与えることになり、free の趣旨とは別物になる。
2. **ツール側の使いやすさ**: 残量を超える散水を、エラーではなく「残量までに切り詰めて実行（切り詰めた旨を返す）」にする、または最小量を満たさない要求を事前に伝える。無駄な失敗（plan で21回）を減らせる。
3. **思考モードをオン**にして hybrid / plan を試す（計画能力が原因なら改善するはず。1呼び出しが数十秒に増える）。
4. 別のモデル（クラウドLLMなど）で、同じ状況・同じ構成を比較する。
