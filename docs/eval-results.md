実行: `uv run pytest evals -m eval`（各シナリオ5回試行、基準は4回以上）。生データは `runs/evals/*.json`（gitignore）。
モデル: Ollama `qwen3:14b`（思考オフ, temperature=0）。

### 観察
- **v1**: ツールを一切呼ばず、最初の返答で最終回答JSON（要約に `get_plant_state` と書く）を返して終了。
  原因は「最終回答はJSON」という指示を、ツール呼び出し前の返答と解釈したこと。
- **v2**（ツールを先に呼ぶ・最終回答は実行後）: ツール呼び出しは成立した（状態確認→天気→行動）。
  ただし**状況に応じた判断になっていない**。どのシナリオでも ほぼ同じ手順
  （`get_plant_state → get_weather → move_to_spot(C) → irrigate(1000)`）を取り、
  雨の予報・日影での適正水分でも歩道Cへ移動して散水した（「Cは冷却需要が最大」を過剰に重視している疑い）。
  ツールエラー・LLM失敗は0件。
- **評価設計の学び**: 「行動しない」系のシナリオだけでは、何もしないエージェントが合格してしまう。
  「行動すべき」系のシナリオを必ず対にしておくことで、v1 の欠陥を検出できた。

## 2026-10-20 プロンプト改善（v3 → v5）

同じ評価シナリオ（各5回、基準4回以上）・同じモデル（qwen3:14b、思考オフ、temperature=0）で比較。

| シナリオ | v1 | v2 | v3 | v4 | v5 |
| --- | --- | --- | --- | --- | --- |
| 強い雨の予報 → 散水しない | ※ | 0 | 5 | **0** | 5 |
| 雨なし・乾燥 → 散水する | 0 | 0 | **0** | 5 | 5 |
| 猛暑の日向・水分少 → 退避か散水 | 0 | 5 | **0** | 5 | 5 |
| 日影・適正水分 → 何もしない | ※ | 0 | 5 | 5 | 5 |
| バッテリー少 → 移動しない | ※ | 5 | 5 | 5 | 5 |
| 行動前に get_plant_state | 0 | 5 | 5 | 5 | 5 |
| 散水量がタンク残量以内 | ※ | 5 | 5 | **0** | 5 |
| 直前に移動 → 理由なく戻らない | ※ | 5 | 5 | 5 | **0** |
| **合格** | 5/8※ | 5/8 | 6/8 | 6/8 | **7/8** |

※ v1 は全試行でツール呼び出し0回（空振り合格）。表の数字は成功回数（/5）。

### 各版の変更と学び
- **v3**: 判断を「上から順に評価する条件→行動」のチェックリストにし、暑熱緩和を副次目的へ格下げ、座標を固定。
  → 雨でも散水する問題が解消。一方、条件を誤判定し、行動を最終回答に書くだけでツールを呼ばない失敗が残った。
- **v4**: 各行を数値で ○/× 判定した判断メモを書かせ、「ツールを呼んでいない行動は実行したと書かない」を明記。
  → 乾燥・猛暑退避は解消したが、雨で `get_weather` を呼ばず散水、タンク120mlで1000mlを試みる退行。
- **v5**: 「両方の観測結果を得るまで行動ツールを呼ばない」「散水量は1000mlと残量の小さい方」を明文化。→ 7/8。
- **残課題**: 「直前にA→Bへ退避した直後、Bで適正水分なのに Aへ戻る」（往復）。チェックリスト #5（何もしない）に反して移動している。

### 評価設計・手法についての学び
1. **試行がほぼ同一**: temperature=0 のため、5回の試行は全シナリオでトレースが完全一致（異なるトレース数=1）。
   実質の標本数は1で、「5回中4回」は統計的な意味を持たない。→ 試行ごとに初期値を少し振る（水分±数%、タンク量、気温）か、temperature>0 にする。
2. **プロンプト修正は他の挙動を動かす**: v3→v4 は2件直して別の2件を壊した。1件ずつの修正でなく、毎回全シナリオで回帰を見る必要がある（評価シナリオの価値）。
3. **シナリオが学習データ化する危険**: 評価シナリオに合わせてルールを書いているため、合格率は汎化性能を意味しない。未見の状況（フェーズ3の24時間シミュレーション）で確認する。
4. **「行動しない」系だけの評価は空振りを許す**: 「行動すべき」系を対で用意したから v1 を検出できた。
5. **思考オフのモデルは条件判定が雑**: 数値を書かせる、観測の前提条件を明文化する、が効いた。思考オン（1呼び出し数十秒）との比較は未実施。

- 試行ごとのばらつき導入（上記1）。
- 24時間シミュレーション（フェーズ3）で v5 の汎化を確認。

## 2026-10-20 往復移動の対策（v6 + 世界側ガード）

### 構造的な対策（BDD: tests/features/world/movement.feature ほか）
1. **世界側ガード**: 直前の移動元へ2時間以内に戻る `move_to_spot` を `RECENT_REVERSAL` で拒否（エラーに `retry_after_hours`）。
   健康度 50 未満は緊急として許可。LLM が誤っても往復が起きない安全網（決定論テストで保証）。
2. **観測の追加**: `get_plant_state` が `last_move`（from / to / hours_ago）を返す。履歴の文章に頼らず構造化データで読める。
3. **プロンプト v6**: `last_move` の読み方と往復禁止を明記（v5 からの差分はこの1項目のみ）。

### 結果（v6、全9シナリオ）: 8/9 合格・回帰なし
| シナリオ | v5 | v6 |
| --- | --- | --- |
| 雨予報 / 乾燥 / 猛暑退避 / 日影 / バッテリー少 / 状態確認 / タンク上限（7件） | 5/5 | 5/5 |
| 直前に移動 → 戻らない【履歴の文章のみ・世界に記録なし】 | 0/5 | **0/5** |
| 直前の移動が世界にも記録されている → 往復を**試みない**（新規） | － | **5/5** |

### 解釈
- 世界にも `last_move` がある**現実的な状況**では、LLM は `last_move` を読んで往復を試みない（5/5）。さらにガードがあるため、仮に試みても移動は成立しない（二重の安全策）。
- **履歴の文章だけ**を与える元のシナリオは 0/5 のまま。この状態（世界に記録が無いのに履歴だけ「移動した」）は実際のシミュレーションでは起きない。
  ただし「LLM は文章の履歴を判断に使えていない」という弱さは残っている（ターン間の持ち越しを文章で行う設計の限界）。
  シナリオは失敗を隠さず残している。フェーズ3で24時間通しの挙動を見て、必要なら履歴の渡し方（構造化）を見直す。
- 学び: LLM の誤りを**プロンプトで直す**より、**世界のルールで不可能にし、必要な事実を構造化データで観測させる**ほうが堅牢（失敗が決定論的テストで保証できる）。

## 2026-10-21 24時間シミュレーションでの実LLM（v6, qwen3:14b）

`vmgs run --agent llm --provider ollama --model qwen3:14b`（猛暑日 heatwave と tradeoff preset）。評価シナリオ（単発判断）とは別の、通し運用での挙動。

| 指標 | heatwave 24h: LLM | baseline | 放置(A) | tradeoff 10h: LLM | baseline |
| --- | --- | --- | --- | --- | --- |
| 最終健康度 | 100.0 | 100.0 | 44.0 | 100.0 | 100.0 |
| 最低健康度 | 98.2 | 99.9 | 44.0 | 97.6 | 97.6 |
| 暑熱緩和スコア | **30.3** | 11.7 | 0 | 11.7 | 11.7 |
| 移動（うち無駄） | 5（**4**） | 1（0） | 0 | 1（0） | 1（0） |
| 散水(ml) | 2000 | 2000 | 0 | 1500 | 1500 |
| 最終バッテリー | **62.0%** | 88.0% | 97.1% | 85.8% | 85.8% |
| 判断失敗 / ツールエラー | 0 / 1 | 0 / 0 | － | 0 / 0 | 0 / 0 |

### 観察
1. **植物ケアはベースラインと同等**。tradeoff では水と電池が足りない状況で、ベースラインと同じ手順（Bへ退避→散水）を取った。
2. **A↔B の往復（ピンポン）が24hで再発**。08:00 A→B、11:00 B→A、13:00 A→B、15:00 B→A、20:00 A→B。バッテリーを 88% → 62% まで消費。
   世界側ガード（直前の移動元へ2時間以内の復帰を拒否）は、**ちょうど2〜3時間おきに戻る**ため発動しなかった。
   単発評価では 5/5 だったのに、通しで出た＝評価シナリオの合格は汎化を保証しない（前節の学び3を実データで確認）。
3. **宣言と実行の不一致が残る**: 「B へ移動」と答えたのに `move_to_spot` を呼んでいないステップが各ランに1件（heatwave 07:00、tradeoff 17:00）。
4. **要約が崩れる**: 最終回答がJSONにならず、判断メモがそのまま `action_summary` に入るステップが多い（heatwave 9/24、tradeoff 2/10）。
   v4 以降の「判断メモを先に書く」指示の副作用で、次ターンへ引き継ぐ要約の質が落ちる。
5. **暑熱緩和は LLM が上**（30.3 vs 11.7）が、移動と電池を犠牲にした結果で、純粋な優位とは言えない。

### 次の改善候補
- ピンポン対策: クールダウンを延ばす／往復を「直近N時間の移動回数」で制限する／`get_plant_state` に直近の移動履歴を複数件返す。ベースラインの挙動（日影に退避したら留まる）を手本にしたヒステリシスも検討。
- 要約の崩れ: 判断メモと最終回答を分離する（最終回答だけをJSONで求める、または構造化出力を使う）。
- 宣言のみのステップ: 最終回答の行動要約と実際のツール呼び出しを突き合わせ、不一致を指標（フェーズ4）に加える。
- フェーズ4: LangSmith でトークン・レイテンシ・推論ログを可視化し、上記を同一シナリオで比較する。
